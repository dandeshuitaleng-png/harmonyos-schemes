# 01 北斗邻援：近场摘要交换与冲突保留门禁

> 状态：已完成 SDK 静态可行性核查；未获得权限、双设备或运行时证据。更新时间：2026-08-31。

## 已核实的本机 SDK 能力

- `@kit.NearLinkKit` 在本机 SDK 中存在，版本从 API `5.0.1(13)` 开始提供；本工程目标 API `6.1.0(23)` 的 phone/tablet system capability 清单包含 `SystemCapability.Communication.NearLink.Core`。
- `manager.isNearLinkSupported()` 可在运行时判断硬件/系统支持；`dataTransfer.createPort`、`connect`、`writeData` 与 `readData` 可建立应用 UUID 的数据收发通道。
- 这些数据传输 API 均要求 `ohos.permission.ACCESS_NEARLINK`，并可能返回权限拒绝、能力不支持、功能关闭、拥塞或连接失败。静态声明不等于当前设备可用。

## 首版交换协议（必须在实现前确认）

1. 用户先在本机记录中选择一条或多条记录，再看见将要交换的字段与接收风险；禁止后台扫描、自动配对或自动发送。
2. 仅交换最小摘要：事件 ID、类型、创建时间、来源标识、位置精度、审核状态、协议版本与摘要完整性字段；精确坐标、联系人和隐私选择不进入近场包。
3. 应用层加密、密钥协商/轮换、身份确认、重放保护和传输失败后的删除策略必须先有已审查协议；NearLink 的传输通道本身不能被表述为已满足本项目的“加密摘要”承诺。
4. 收到摘要不得覆盖本机记录。相同 `eventId` 且内容摘要不同，建立同一 `conflictGroupId` 下的两份不可变版本，分别保留来源与接收时间；用户之后再决定是否导出或提交。

## 运行时验收前置条件

- 两台可见且支持 NearLink 的测试设备；各自明确授予 `ACCESS_NEARLINK`。
- 已定义并评审应用 UUID、数据上限、协议版本、密钥策略与断开/拥塞恢复。
- 真机完成：拒绝权限、功能关闭、不支持设备、取消、成功发送、成功接收、重复摘要、冲突摘要和重启恢复。

## 当前结论

可把 NearLink 作为**待验证的原生近场候选**，但当前工程没有权限声明、协议实现、双机测试或加密/冲突运行时证据；不得称为已支持近场互传或已完成加密。
